Hands-on — run the real thing

Time: ~15 minutes at the keyboard. Tangible win: a Cadence server running on your Mac, a real workflow executing, and the moment of truth — you kill the worker mid-run and watch Cadence resume it. This is where durable execution stops being theory.

Ian — every prior lesson was a mental model. This one you run. The payoff is the crash-and-resume demo you can't get from the ICM folder approach. Do this in a scratch checkout first; we port to the research pipeline afterward. Follow the steps in order and watch the feedback at each one.

Primary source Get Started with Cadence (the 5-minute SQLite quickstart) and Golang Hello World. The runnable Go is the cadence-samples repo. Commands below are copied from the official quickstart — verify against it as versions move.

Good news: no Docker required The official quickstart now uses an embedded SQLite backend. No Cassandra, no docker-compose, no cluster. One clone, one build, one server process. This is the fastest possible path to a running Cadence.

Step 1 — Start a local server

Clone and build the server, install the SQLite schema, and start it:

# Clone and build (needs Go + make)
git clone https://github.com/cadence-workflow/cadence.git
cd cadence
make bins

# Install the schema and start the server on the embedded SQLite backend
make install-schema-sqlite
./cadence-server --zone sqlite start

Feedback to look for: the server logs start streaming and stay running. Leave this terminal open — it is your Cadence brain.

Step 2 — Open the Web UI

In a browser, go to http://localhost:8088. This is Cadence Web — you'll watch your workflow's event history here, which is the single best way to see durable execution working.

Feedback to look for: the Cadence Web dashboard loads. No workflows yet — that's next.

Step 3 — Register a domain

Workflows live in a domain (Lesson 1's glossary). Register one with the CLI before running anything:

# From the cadence repo; registers a domain named "research"
./cadence --domain research domain register
# Verify it exists:
./cadence --domain research domain describe

Feedback to look for: domain describe prints the domain's details instead of a "not found" error.

Step 4 — Run the Hello World workflow

In a second checkout, get the samples, point them at your local server, and run the worker + starter:

git clone https://github.com/cadence-workflow/cadence-samples.git
cd cadence-samples
make   # builds the sample binaries

# Start the worker (hosts the workflow + activity code):
./bin/helloworld -m worker &

# In another terminal, trigger a run (the starter):
./bin/helloworld -m trigger

Feedback to look for: the worker logs the activity running and the workflow completing. Refresh Cadence Web — you'll see a completed workflow with its full event history. Read that history: every step Cadence recorded is what makes replay possible.

Step 5 — The moment of truth: crash and resume

This is the whole point. Use a workflow with a durable sleep (the sleep sample, or add a workflow.Sleep(ctx, 60*time.Second) between two activities), then:

1. Trigger the workflow. It runs the first activity, then hits the sleep. 2. While it is sleeping (or mid-activity), Ctrl-C the WORKER process. ← crash 3. In Cadence Web, the workflow is still there — Running, parked, not lost. 4. Restart the worker: ./bin/helloworld -m worker 5. Watch: the worker picks the workflow back up, Cadence REPLAYS its history, and it CONTINUES from the sleep — the first activity does NOT run again.

Feedback to look for: after restart, the workflow completes, and the event history in Cadence Web shows the first activity ran once. That is durable execution — the thing your ICM pipeline can't do without you manually re-running a stage folder.

If something breaks Most first-run failures are one of: server terminal was closed (restart it), domain not registered (Step 3), or the sample pointing at the wrong host/port (check its config against 127.0.0.1:7933). The Workflow Troubleshooting page and the CNCF Slack are the fastest unblocks. And ask me — that's what I'm here for.

Step 6 — Port a slice to your pipeline

Once the sample crash-resumes, you've proven the engine. Now build the smallest real slice: a ResearchWorkflow that runs two of your seven stages as activities (say coordination → execution), with one workflow.Sleep or one signal gate between them. Run it, crash it, resume it. That slice — not the whole pipeline — is enough evidence to make the mission's call: does durable execution earn its operational cost for your research workflow, or does the simpler ICM/folder model still win?

What "done" looks like for this workspace You can (1) run a Cadence workflow locally, (2) crash the worker and watch it resume, (3) add a human-signal gate and a durable timer, and (4) state, with the slice as evidence, where Cadence beats ICM for your pipeline and where it doesn't. That's the mission.
