How a lakehouse is built

Lesson 5 of 8. Time: 10 minutes. Tangible win: map each warehouse component to its lakehouse counterpart.

Now the answer. A lakehouse keeps the same six components but separates them and stores data in open formats, so any compatible engine can use it. Source: Sections 4 and 5.1.

Six traits of a lakehouse

The paper characterizes a lakehouse by: transactional support, open data, no copy, data quality and governance, schema management, and scalability through separate storage and compute.

Component mapping

ComponentWarehouseLakehouse (paper's examples)
StorageBundledCloud object stores: Amazon S3, Azure Storage, Google Cloud Storage
File formatProprietaryOpen, usually columnar: Apache Parquet
Table formatProprietaryApache Iceberg, Apache Hudi, Delta Lake
Storage engineBundledCompaction, repartitioning, indexing services
CatalogBundledSeparate service: Hive, AWS Glue, Nessie, REST
Compute engineOne engineChoose per workload: Spark, Flink, Dremio Sonar
The key idea

The table format is a metadata layer over open files. The paper credits it with bringing schema evolution, partitioning, time travel, and ACID transactions to a data lake, where they were previously limited to warehouses.

Retrieval check

What does storing data in open file and table formats allow?

Correct. Open formats let different engines, even from different vendors, work on the same data.

Not quite. Open formats remove single-vendor control, and catalogs are still used. The benefit is multiple engines on one copy.
