# Mission: Data lakehouse architecture

## Why
Enable teammates and review technical content on data lakehouse architecture. That means being able to explain it clearly, separate vendor argument from evidence, and recommend a sensible setup for a given workload.

## Success looks like
- Explain to a colleague, without notes, what a lakehouse is and why it exists.
- Judge vendor claims: name which statements in a source are architectural arguments and what you would test.
- Compare Apache Iceberg, Apache Hudi, and Delta Lake for a given use case and pick one with reasons.
- Sketch a reference setup (storage, file format, table format, catalog, engines) for a stated workload.

## Constraints
- Short lessons, one tangible win each.
- The source paper is written by a vendor (Dremio), so lessons attribute claims to it and flag them for independent checking.
- Table format comparison and reference design need sources beyond the paper.

## Out of scope
- Tuning or operating a specific product.
- Benchmarking performance or cost.
