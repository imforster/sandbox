Composing Questions into a Workflow

Time: 8 minutes. Tangible win: you can turn one multi-question Jev call plus plain code into the "AI traffic cop" that triages an email end to end.

Ryan Vogel's phrase in the transcript is the whole mental model: Jev is an AI traffic cop at the front of an expensive queue. This lesson wires the three question types from Lesson 2 and the thresholds from Lesson 3 into one working triage flow.

Primary source Composite scoring and intent routing — TypeSafe patterns docs (~6 min). The building blocks for combining several decisions into one branch.

The shape of a workflow

The docs are blunt about this: the most reliable real-world workflows are many independent, decomposed questions, with fine-grained branching driven by probabilities rather than one big discrete decision. You ask everything in one call — questions run in parallel, so extra questions barely cost latency — then let ordinary code combine the typed answers.

The traffic cop, in code

One call gets every decision. The logic that acts on them is boring, deterministic Python — which is the point:

from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()

def triage(email: str) -> dict:
    r = client.system_one(
        state=email,
        questions={
            "category": Choice(
                instructions="Bucket this email",
                criteria={
                    "work": "Job or project related",
                    "finance": "Payments, invoices, banking",
                    "marketing": "Promotions and newsletters",
                    "security": "Account or login alerts",
                },
            ),
            "priority": Score(
                instructions="How urgently this needs attention",
                criteria=["Low", "Medium", "High", "Urgent"],
            ),
            "is_spam": Noul(instructions="This email is spam"),
            "warrants_reply": Score(
                instructions="How much this warrants a personal reply",
                criteria=["Ignore", "Maybe", "Should reply"],
            ),
        },
    )
    a = r.answers

    # boring, deterministic branching on typed answers
    if a["is_spam"].noul >= 0.95:
        return {"action": "archive", "reason": "spam"}
    if a["priority"].score >= 2.5 and a["category"].confidence >= 0.80:
        return {"action": "notify_now", "folder": a["category"].choice}
    if a["warrants_reply"].score >= 1.5:
        return {"action": "draft_reply", "folder": a["category"].choice}
    return {"action": "file", "folder": a["category"].choice}
Decompose, don't cram

Four small questions beat one giant "what should I do with this email?" question. Each answer is independently calibrated, so your branch can weigh spam confidence differently from priority. This is why the docs push many fine-grained questions over one big one.

Where the LLM comes back in

Notice draft_reply — Jev decided the email deserves a reply, but writing that reply is open-ended text, an LLM job. Jev routes; the LLM generates. That hand-off is the whole harness pattern, and it's the subject of Lesson 5.

Retrieval check

Why ask category, priority, spam, and reply as four separate questions instead of one "what do I do" question?

Right. Decomposed questions each carry their own calibrated confidence, so your code can weigh spam and priority separately. Parallel evaluation means four questions cost about the same latency as one.

Speed isn't the reason — questions run in parallel. The point is that separate questions are separately calibrated, so your branch can treat each confidence independently.

Practice

  1. Take one queue from your own work (support, leads, PRs) and list its decomposed questions.
  2. Assign each a type and write the questions dict.
  3. Write the branch: which outcomes act, which draft with an LLM, which escalate to a human.
  4. Bring it back — I'll pressure-test whether any question is secretly two questions.
