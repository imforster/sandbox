What fullstack-agent Actually Is

Time: 7 minutes. Tangible win: an accurate mental model of the system, cut free of its marketing.

Ian — before you can evaluate this project or borrow from it, you need an accurate mental model. The README is persuasive and slightly misleading. This lesson gives you one thing: the true shape of the system, grounded in its source files rather than its sales copy.

The naming trap "fullstack-agent" does not mean an agent that writes full-stack code, and it is not an agent framework you build on. It means an agent that has a stack: memory, voice, face, hands. The README says so outright: "Not an agent that writes full-stack code. An agent that HAS a full stack."
Primary source Read the installer spec itself: fullstack-agent.md. It is the highest-value artifact in the project and the source for every later lesson. Skim Phases 0 through 4 and notice how much is principle versus procedure.

The two-sentence truth

fullstack-agent is a Claude-Code-only installer wizard that assembles four independent single-purpose repos into one desktop assistant. The installer itself is a prose document (fullstack-agent.md) that Claude Code reads and executes as a conversation — there is no compiled application here.

The four pieces

PieceRepoDoes
Mindai-memory-vaultPlain-text file memory the AI reads and writes
MouthbacktalkPush-to-talk voice in and out
Faceai-visualizerBrowser visualizer synced to conversation
Handsbarehands (optional)Webcam gesture control

Each is its own repo, and each works alone. fullstack-agent's only job is to compose them and wire them together.

The shape, drawn

home folder (the agent "lives" here — Claude Code opens here) │ ├── fullstack-agent/ the toolbox: installer + start/update scripts │ └── fullstack-agent.md the wizard, as prose the LLM executes │ ├── CLAUDE.md the agent's identity + "you are the mechanic" │ ├── ai-memory-vault/ ─┐ ├── backtalk/ │ four sibling repos, cloned in, ├── ai-visualizer/ │ wired only by config file paths └── barehands/ ─┘ (voice writes status files → face reads them = the only "bus")
The one insight to keep The pieces are loosely coupled by the filesystem. They share no library and no API. They connect by writing each other's paths into JSON config, and they communicate at runtime through small status files in a shared directory. That is the whole integration model. Later lessons judge whether that is clever or fragile.

Why this matters for your mission

You want reusable composition patterns, not a Jarvis. The valuable ideas here are architectural: file-based memory, config-path wiring, a status-file bus, "adopt never destroy," and self-healing troubleshooting docs. The voice, face, and hands are just case studies of those patterns. We will name and judge each one against your own Go, AWS, and simplicity defaults.
