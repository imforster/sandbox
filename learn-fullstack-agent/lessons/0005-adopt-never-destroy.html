Adopt, Never Destroy

Time: 7 minutes. Tangible win: a concrete safety principle for any tool that installs into a user's existing environment.

Ian — the most transferable principle in this whole project has nothing to do with voice or faces. It is how the installer treats state it did not create. The rule, stated verbatim and repeated across the spec: never delete, overwrite, or move anything the person built.

Primary source Read Phase 0 and Phase 3 of fullstack-agent.md. Count how many distinct rules exist just to avoid touching pre-existing vaults, identities, and hand-built pieces.

What the principle is

Adopt-never-destroy means an installer treats pre-existing user state as read-only and sovereign. It finds what exists, keeps it in place, and when it must supersede something, it retires the old thing where it sits and says so out loud — it never deletes, overwrites, or relocates.

How the spec enforces it

SituationBehavior
Existing agent identity foundAdopt it. Skip every identity question. "Found [name], keeping them as they are."
Existing vaultPoint at it by path. Never move it, never read other vaults, never comment on its location.
Hand-built voice/visualizerInstall the new default; the old build "stays right where it is; it just will not be the one that runs."
A custom visualizer scenePromote it: copy (never move) into the gallery beside shipped faces.
Migrating old memoryCopy, never delete the originals; ask which projects to take over.
The principle to keep Destructive-by-default is a trust bomb. Adopt-never-destroy makes the tool safe to run on a machine you care about, and — critically — safe to run twice. Idempotent, non-destructive installs are the difference between a tool people trust and one they run only in a throwaway VM.

Where it costs you

The principle is not free. Detecting existing state is real work — much of the spec's complexity is adoption logic. "Retire in place" leaves clutter: old builds accumulate on disk. And "never move" forces coordination by configuration paths (Lesson 4) rather than convention, which is more wiring. You pay in complexity and disk to buy trust. For a personal-machine installer that trade is clearly right; for a disposable container it may be over-engineering.

Applying it to your work

This maps straight onto your production-safety rules and your own me.md ("Backwards Compatibility — don't break existing consumers"; "Surgical Changes"). The generalization: any code that writes into an environment it did not create should default to additive and reversible. Read before write. Confirm before replace. Retire, don't delete. It is the install-time version of a two-way-door decision — and it is exactly the posture your steering files already ask of agents touching your systems.
