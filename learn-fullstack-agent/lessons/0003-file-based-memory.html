File-Based Memory

Time: 8 minutes. Tangible win: judge when plain-text files are the right memory substrate for an agent — and when they are not.

Ian — the "mind" of this stack is ai-memory-vault: an Obsidian vault of plain Markdown the agent reads and writes. No database, no vector store. This lesson extracts the pattern and its limits so you can decide where it fits your own systems.

Primary source Read the ai-memory-vault README. Note three claims to test: memory "lives outside the model with no size ceiling," the agent "pulls back exactly what it needs in one step," and the concept of AI priming.

What the pattern is

File-based memory stores durable state as human-readable files in a directory tree, and lets the agent retrieve by navigating that tree (folders, filenames, links) rather than querying an index. The vault is the source of truth; the model holds only what the current task needs and reaches the rest in one file read.

Why plain text, specifically

PropertyPayoff
Human-readableYou can see, edit, and correct the agent's memory directly. No opaque store.
PortableMarkdown outlives any tool. No lock-in to a DB or embedding model.
Diff-able / versionableGit tracks memory changes; you get history and rollback for free.
No size ceiling in contextThe vault can be huge; only the retrieved slice enters the window.
Structured by conventionFolders and links are the schema — "AI priming" points the agent at the right notes per job.
The insight to keep Retrieval here is navigational, not semantic. The agent finds a note because a folder, filename, or link told it where to look — the same way you would. That is cheap, transparent, and correctable, and it is why it works without a vector database.

Where it fails

Navigational retrieval degrades as the corpus grows unstructured. If notes are not organized by convention, the agent cannot find them — there is no similarity search to fall back on. It scales with human-maintained structure, not with volume. Fuzzy recall ("find everything related to X" across thousands of notes with no link) is exactly what a vector store does and files do not. And concurrent writers can clobber a file — plain text has no transaction model.

Applying it to your work

Your AIOS is already this pattern — Markdown files (me.md, wikis, journals) the agent primes on. The lesson to carry: file-based memory is the right default for durable, low-write, human-owned knowledge where transparency matters more than fuzzy recall. When you need cross-corpus similarity search at scale, add a vector index beside the files, not instead of them — keep the readable files as truth and treat the index as a derived cache.
