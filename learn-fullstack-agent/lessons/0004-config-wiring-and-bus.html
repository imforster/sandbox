Config Wiring and the Status-File Bus

Time: 8 minutes. Tangible win: understand filesystem-level component coupling and judge its blast radius against a real message bus.

Ian — this is the integration heart of the stack. Four separate processes coordinate with no shared library and no network API. They connect two ways: config-path wiring at setup, and a status-file bus at runtime. Both are just the filesystem.

Primary source Read the backtalk README ("Give it a face") and Phase 4 of fullstack-agent.md. backtalk "writes tiny state files while it listens, thinks, and speaks, so anything can watch them and react in real time."

The two mechanisms

MechanismWhenHow
Config-path wiringSetupThe wizard writes each piece's path into the others' JSON — e.g. bus_dir, agent_dir, barehands_state_dir.
Status-file busRuntimeThe voice writes small state files (listening/thinking/speaking); the face polls that directory and reacts.
setup (config-path wiring) wizard ──writes paths──> backtalk.json, ai-visualizer.json, barehands.json runtime (status-file bus) backtalk ──writes──> [bus_dir]/state.* <──reads── ai-visualizer <──reads── barehands (one writer, many readers, filesystem is the broker)
The insight to keep This is a one-writer, many-reader pub/sub over the filesystem. The producer never knows who consumes it. You can add a fifth face tomorrow that reads the same files, and the voice needs zero changes. That is genuine loose coupling, achieved with nothing but a shared directory.

Why it is clever

No message broker to run, no ports, no service discovery, no serialization contract beyond "small files." Any language can participate — a reader is a directory poll. It degrades gracefully: a reader that dies leaves the writer untouched. For a single-user desktop app, this is radically less machinery than Redis, a socket protocol, or an event bus, and it is inspectable — you can cat the bus.

Where it fails

Name the limits, because they are exactly where you would not use it. Polling has latency and wastes cycles versus event-driven push. There is no delivery guarantee, ordering, or replay — a reader that was asleep misses the transition. It does not cross machines (a shared directory is local). Filesystem watching has real cross-platform quirks. And many writers to one file race, since there is no transaction. It suits local, ephemeral, one-writer status signaling and nothing heavier.

Applying it to your work

For AWS-native systems your instinct will be EventBridge, SNS/SQS, or a socket — correct for anything distributed or durable. But the status-file pattern earns its place for local dev tooling and single-host coordination: a Go CLI that drops JSON status into a temp dir for a watcher to render. The judgment: use the filesystem bus when the blast radius is one machine and the data is disposable status; reach for a broker the moment you need delivery guarantees or cross-host reach.
