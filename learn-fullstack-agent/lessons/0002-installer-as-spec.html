The Installer-as-Spec Pattern

Time: 8 minutes. Tangible win: decide when a prose spec executed by an LLM beats writing an installer in code.

Ian — the single most unusual thing about this project is that its installer is not a program. It is fullstack-agent.md, a prose document the LLM reads and performs. This lesson names that pattern and gives you a rule for when to reach for it.

Primary source Re-read fullstack-agent.md as an artifact, not instructions. Notice it mixes hard procedure (exact git commands, JSON keys) with soft judgment ("if they shrug, door A").

What the pattern is

An installer-as-spec expresses install logic as natural-language steps plus embedded commands, and delegates execution to an agent. The agent supplies the parts a script cannot: reading existing state, asking one clarifying question, adapting order, and recovering from partial failure by re-reading the current situation rather than replaying fixed steps.

Why it works here

ForceHow the spec exploits it
Highly variable machinesProse says "check for git; if missing, ask, then install" instead of branching code for every OS and shell state.
Existing user state"Find what already exists" is a judgment task; the agent inspects and decides, no rigid detection logic.
Plain-English UXThe install is the conversation, so the spec and the user-facing experience are the same text.
Self-repairOn failure the agent reads a TROUBLESHOOTING.md and continues; a script would just exit non-zero.
The rule to keep Reach for installer-as-spec when the work is high-variance and judgment-heavy and a human is present to confirm. Reach for real code when the work is repeatable, unattended, or safety-critical — CI, production deploys, anything that must run identically a thousand times.

Where it fails

The costs are real and worth naming for your own systems. Execution is non-deterministic: the same spec can run differently twice. It is unauditable in the CI sense — there is no exit code, no diff of "what it will do" before it does it. It is slow and expensive per run (every step is model tokens). And it cannot be unit-tested; you test it by running it and watching.

real code installer installer-as-spec deterministic adapts per machine fast, free to re-run slow, token-cost per run testable, CI-safe unattended-unsafe rigid on new state handles novel state exit codes + logs conversation + judgment

Applying it to your work

You already run this pattern — Kiro steering files and skills are installer-as-spec for behavior, not setup. The transferable move is deciding the boundary: keep the deterministic core (the git clone, the JSON write) as literal commands the agent runs verbatim, and let prose own only the judgment around them. That hybrid is exactly what fullstack-agent.md does, and it is the safe version of the pattern.
