Review & Orchestrate

Lesson 5 · Leverage Devin on a New Project · ~8 minutes

You can now scope, onboard, and run a single session well. The last leap in leverage is two-fold: reviewing Devin’s output efficiently, and orchestrating more than one agent at once. As coding agents write more, the bottleneck shifts from writing code to reviewing it — so both skills matter.

Your win

Let Devin Review catch bugs in a closed loop, and delegate independent work to subagents so several tasks progress in parallel — while you stay the reviewer, not the typist.

Review: close the loop with Devin Review

Devin Review turns a large PR into an organized diff with a Bug Catcher (bugs by severity), a security scan (CWE-classified), and informational flags. Trigger it on any connected GitHub PR by commenting /devin review.

The force-multiplier is Auto-Fix: when enabled, Devin proposes fixes for the bugs it finds and responds to review comments and CI failures — a closed loop where the PR iterates toward merge-ready without you in the middle of every cycle.

Review the findings, not the confidence

Bug Catcher labels findings by confidence, but you still judge them. Fix severe bugs; investigate flags yourself; ignore style nits your linter already owns. Encode project-specific scrutiny in a REVIEW.md — “all changes to src/auth/ need a security check” — so every review enforces it.

Orchestrate: delegate to subagents

A session can spawn subagents — independent workers that share your tools and codebase but run in their own conversation. Ask for them explicitly (“research how auth works in a subagent”), or let Devin delegate on its own. Cognition reports subagents both improve coding performance and reduce cost.

Foreground

Runs inline; the parent pauses and waits. You approve tool calls as they come. Best for one focused sub-task you want to watch.

Background

Runs in parallel while the parent keeps working. Uses only pre-approved tools; anything new is auto-denied. Best for fan-out work.

Two built-in profiles decide capability and cost:

ProfileCan it write?Model & cost
subagent_exploreRead-only researchCheap default model (SWE-1.6) — use for exploration
subagent_generalFull code changesSame model as the parent — a full extra session’s cost
Cost scales with fan-out

Each subagent is its own session with its own context and inference calls. Fanning out many subagent_general workers on a premium model multiplies spend. Ask for an explore subagent when the work is research, and reserve write-capable subagents for real parallel implementation.

The parallel workflow

Root session
├── explore subagent   → "map the payment module"   (read-only, cheap)
├── general subagent A → implement webhook handler   (background, parallel)
└── general subagent B → implement settings page     (background, parallel)
        ↓
   parent summarizes each result → you review the PRs with /devin review

This is the same decomposition from the 3-hour rule (Lesson 2), now executed concurrently. You return to being the reviewer of finished work rather than the driver of each keystroke.

Do This Now

  1. Open a Devin-authored PR and comment /devin review; triage the findings.
  2. Add a REVIEW.md naming one area that needs extra scrutiny.
  3. In a session, ask Devin to “research X in an explore subagent” and watch the panel.
  4. Split one real task into two independent slices and run them as background subagents.
