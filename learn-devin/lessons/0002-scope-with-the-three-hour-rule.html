Scope with the 3-Hour Rule

Lesson 2 · Leverage Devin on a New Project · ~7 minutes

You know Devin’s five modes from Lesson 1. The next lever is the one that decides whether a session succeeds before Devin writes a line: scope. Under-scope and Devin drifts; over-scope and it stalls halfway through a sprawling task.

Your win

Cognition’s rule of thumb: if a task would take you three hours or less, Devin can most likely do it. For larger work, break it into focused sessions and run them in parallel.

Why three hours

The number is a proxy for a task you could fully specify to a competent teammate in one handoff. A three-hour task has a clear boundary, a knowable success condition, and rarely branches into open-ended design. That is exactly the shape Devin handles best. Anything bigger usually hides several decisions that Devin will make for you — often not the way you would.

The stall pattern

“Improve our database’s performance” is not a task; it is a project. Devin cannot tell when it is done. Give it “add a composite index on order_id and product_id, replace the correlated subquery in getOrderDetails with a JOIN” instead — a bounded three-hour slice with a testable result.

The three-part scope

Every well-scoped task carries three things, just like a handoff to a coworker:

PartQuestion it answersExample
ContextWhere and why?“In the login route of the auth service…”
DirectiveDo what, exactly?“…add rate limiting: 5 attempts per minute per IP.”
Success criteriaHow do we know it’s done?“A 6th attempt returns HTTP 429; add a unit test that proves it.”

The success criteria are the part people skip — and the part that most determines whether you trust the result. “Make sure it works” is not a criterion. “Endpoint returns 200 and includes all required fields” is.

Splitting a big task

When a task exceeds three hours, decompose it into verifiable sub-tasks and start one session per sub-task. Ask Devin to report back at each checkpoint.

Project: "Add team billing"        (~2 days — too big)
        │
        ├─ Session A: DB schema + migration for plans/subscriptions
        ├─ Session B: Stripe webhook handler (idempotent)  ← independent
        └─ Session C: /billing settings page               ← independent
                                                              run in parallel

Independent slices run in parallel; dependent ones run in sequence. We orchestrate parallel sessions properly in Lesson 5.

Check Your Understanding

Which task is best scoped for a single Devin session?
  • Rebuild the whole reporting dashboard to be faster overall
  • Add a cached count endpoint returning active users daily
  • Improve the general performance across our backend services
Correct. It is bounded, under three hours, and has a testable success condition.
Not quite. “Rebuild” and “improve general performance” are open-ended projects with no clear done state. The cached endpoint is the bounded slice.
Which element most determines whether you can trust Devin’s result?
  • The polite tone you use when writing out the request
  • The number of files you attach as context up front
  • The explicit, testable success criteria you define
Correct. Testable success criteria let both Devin and you verify “done.”
Not quite. Tone and file count help, but explicit testable success criteria are what make the result verifiable.

Do This Now

  1. Pick one task on your new project you were about to hand Devin.
  2. Estimate it. Over three hours? Split it into sub-tasks first.
  3. Write the three parts: context, directive, success criteria.
  4. Make the success criteria testable — a command, status code, or rendered result.
