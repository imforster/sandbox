Onboard Your Repo

Lesson 3 · Leverage Devin on a New Project · ~8 minutes

A well-scoped task (Lesson 2) still fails if Devin doesn’t know how your project runs. Onboarding is the one-time investment that makes every later session start informed instead of guessing. Three layers do the work: indexing, AGENTS.md, and Knowledge.

Your win

Set up three onboarding layers once, and stop repeating the same setup, style, and “how we do things” context in every prompt.

Layer 1 — Index the repository

Indexing lets Devin understand and search your codebase before it works — the foundational step the docs tell you to do before your first session. Without it, Devin reads blind; with it, it navigates like someone who has seen the whole tree. Index the repo from Devin’s repo settings before you scope real work against it.

Layer 2 — Write an AGENTS.md

Devin supports AGENTS.md, an open standard — think of it as a README for agents. Put it in your project root; Devin reads it before it starts coding. Cover the things a new teammate would ask on day one:

# AGENTS.md

## Setup Commands
- Install dependencies: `npm install`
- Start dev server: `npm run dev`
- Run tests: `npm test`

## Code Style
- TypeScript strict mode; functional React components
- ESLint + Prettier enforced; conventional commits

## Testing Guidelines
- Unit-test new functions with Jest; aim for >80% coverage
- Run tests before committing

## Project Structure
- `/src` app code · `/tests` tests · `/docs` docs

## Development Workflow
- Feature branches from `main`; PRs for review; squash before merge
Why it pays off

Every fact in AGENTS.md is a decision Devin no longer has to guess. It stops picking the wrong test runner, the wrong branch base, or the wrong commit style — the small mistakes that cost you review time.

Layer 3 — Add Knowledge

For context that should persist across all sessions — coding standards, common bugs and their fixes, how to use internal tools — use Knowledge. Knowledge items are recalled automatically when relevant, so you never repeat them in a prompt. Pin them to a repo or apply them globally.

Knowledge vs. Playbooks — don’t confuse them

Use Knowledge for broad, always-on conventions and context. Use Playbooks for step-by-step procedures tied to a specific repeating task (“address CI build failures”). Knowledge is what’s true; a Playbook is what to do.

How the layers stack

Indexing   → Devin can FIND anything in the codebase
AGENTS.md  → Devin knows HOW to build, test, and style this repo
Knowledge  → Devin remembers WHAT'S TRUE across every session
Playbook   → Devin follows a fixed PROCEDURE for a recurring task

Check Your Understanding

Where do you put “run tests with pytest, not unittest” so Devin reads it before coding?
  • In the AGENTS.md file at your project root directory
  • Inside a one-off comment on the pull request thread
  • Only in the chat prompt each session you happen to start
Correct. AGENTS.md is read before coding and captures setup and testing conventions.
Not quite. A PR comment or per-session prompt won’t be read up front every time — AGENTS.md is.
You have a fixed procedure Devin should follow to triage CI failures. What fits?
  • Store the steps as a broad Knowledge entry pinned globally
  • Create a Playbook capturing the repeatable triage procedure
  • Repeat the steps manually in every single session prompt
Correct. Playbooks capture step-by-step procedures for recurring tasks.
Not quite. Knowledge is for broad always-on context; a fixed procedure belongs in a Playbook.

Do This Now

  1. Index your new project’s repository in Devin.
  2. Add an AGENTS.md at the root with setup, style, testing, and workflow.
  3. Capture one always-true convention as a Knowledge item.
  4. Start an /ask session and confirm Devin answers using your conventions.
