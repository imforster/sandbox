Ask → Plan → Code in Practice

Lesson 4 · Leverage Devin on a New Project · ~8 minutes

You have the five modes (Lesson 1), a scoped task (Lesson 2), and an onboarded repo (Lesson 3). Now run the workflow the docs recommend end-to-end — and write the kind of instruction that gets a mergeable result on the first try.

Your win

The single most important instruction habit: be as specific as you would be handing a detailed spec to a coworker. Devin gets stuck when a request has too many interpretations.

The loop: Ask, then Plan, then Code

/ask    → understand the code, get cited answers      (read-only)
   ↓
/plan   → turn understanding into a scoped prompt      (no changes)
   ↓
/code   → execute the plan, test, open a PR            (writes code)

Each arrow hands context forward. By the time Devin writes code, it is executing a plan you already reviewed — not improvising from a one-line ask.

Write an opinionated instruction

Make the decisions for Devin. Compare:

Don’t

“Improve our database’s performance.”

“Make the app look better.”

“Make sure it works.”

Do

“Add a composite index on order_id and product_id; replace the correlated subquery in getOrderDetails with a JOIN.”

“Refactor the Header to use useReducer; preserve all functionality; add unit tests.”

“Run npm test after each iteration; pass ESLint before pushing.”

The good instructions share four traits the docs call out: they give context, break work into steps, define success criteria, and reference existing patterns (“use authTemplate.rs for error-handling consistency”).

Close the feedback loop

Devin has a full desktop — shell, IDE, browser. Tell it to test its own work before opening a PR, and give it automatic checks to iterate against:

  • “Run npm run dev and verify the new page renders at /settings.”
  • “Open the browser, complete the OAuth flow, confirm it succeeds.”
  • “Pass ESLint/Prettier and the CI pipeline before pushing.”
Set checkpoints

For multi-step tasks, ask Devin to report back after each sub-task: “When modifying the API, confirm the endpoint returns 200 and includes all required fields.” Checkpoints keep it focused and catch drift early.

Check Your Understanding

Which instruction is most likely to get a mergeable result on the first pass?
  • Please try to make the checkout process a lot better overall
  • Add idempotency keys to the checkout POST; test duplicates
  • Look into checkout and fix whatever seems wrong in there
Correct. It is specific, bounded, and states a testable success condition.
Not quite. “Better” and “fix whatever” leave the decisions to Devin. The idempotency-key instruction is specific and testable.
Why tell Devin to run tests and spin up the app itself?
  • It makes the final pull request description read more nicely
  • It lets Devin QA and correct its work before your review
  • It permanently disables the need to review any output later
Correct. Self-testing creates a feedback loop so Devin fixes mistakes before you look.
Not quite. It doesn’t remove review — it means Devin corrects its own errors first, so review is faster.

Do This Now

  1. Take your scoped task from Lesson 2. Open /ask and explore the relevant code.
  2. /plan it into a prompt; read the plan and tighten anything vague.
  3. Switch to Code, add explicit success criteria and a “test it yourself” instruction.
  4. After it finishes, open Session Insights → Generate Analysis for an improved prompt.
